# Internationalisation (FR / EN)

Le français est la langue par défaut. Les URL ne changent pas (`/marche`,
`/actions/SNTS`, …). L'anglais est une préférence de session, pas une
arborescence `[locale]`.

## Comment la langue est choisie

1. Cookie `ouestbourse-locale` (`fr` ou `en`), valable un an, `SameSite=Lax`.
   Il fonctionne pour un visiteur déconnecté : aucune colonne en base, donc
   **pas de migration Prisma**.
2. Premier passage sans cookie : le middleware lit `Accept-Language`.
   L'anglais n'est retenu que s'il est **strictement** préféré au français.
   Sinon, français.
3. Le commutateur FR / EN (en-tête et menu mobile) réécrit le cookie puis
   rafraîchit la page.

Les Server Components lisent la langue via `getI18n()` (`lib/i18n/get-i18n.ts`).
Les Client Components passent par `useI18n()` (`components/i18n/I18nProvider.tsx`),
branché dans `app/layout.tsx`.

Nombres, dates et FCFA : `format` (`fr-FR` ou `en-GB`). Le code monétaire
affiché reste **FCFA** (pas le symbole ISO `XOF`). Les milliards sont
« Mds FCFA » en français et « bn FCFA » en anglais. `N/D` ne change pas.
Les tickers, noms de sociétés, BRVM et SGI ne se traduisent pas. Les signaux
calculés restent `ACHAT FORT` / `ACHAT` / `CONSERVER` / `ALLÉGER` / `VENDRE`
dans les données ; seul l'affichage anglais devient STRONG BUY / BUY / HOLD /
REDUCE / SELL (`labels.signal`).

## Ajouter une chaîne

1. Copier le texte français **tel qu'il est à l'écran** dans
   `lib/i18n/messages/parts/fr/<domaine>.ts`.
2. Ajouter la même clé dans `lib/i18n/messages/parts/en/<domaine>.ts`.
3. Dans un Client Component : `const { t, format, labels } = useI18n()`.
   Dans un Server Component ou `generateMetadata` : `const { t } = getI18n()`.
4. Interpolation : `t("domaine.cle", { nom: "SNTS" })` avec `{nom}` dans les deux langues.
5. `npm test` (ou `npm run i18n:check`) échoue si une clé EN manque, est vide,
   ou recopie une longue phrase française.

## Ajouter une langue plus tard

1. Ajouter le code dans `LOCALES` (`lib/i18n/config.ts`) et dans `negotiateLocale`
   si elle doit être détectée.
2. Dupliquer `lib/i18n/messages/parts/en/` vers `parts/<code>/` et traduire.
3. Enregistrer le paquet dans `lib/i18n/messages/fr.ts` (type source) et
   `lib/i18n/messages/en.ts` n'est plus le seul second dictionnaire :
   étendre `getMessages()` et `DeepStringTree`.
4. Ajouter un bouton dans `components/i18n/LanguageSwitcher.tsx`.
5. Étendre `diffMessageKeys` pour comparer chaque locale au français.
6. Choisir le tag `Intl` (dates, nombres) dans `intlLocale()`.

Une préférence par compte (cookie + colonne `users.locale`) demanderait une
migration Prisma et `prisma migrate deploy` sur la base Supabase de production.
Ce n'est pas en place : le cron d'alertes n'a donc pas de langue utilisateur
et les e-mails de notification restent en français, hors chrome traduit quand
un appel passe une locale. Les e-mails d'auth (confirmation, mot de passe)
suivent le cookie de la requête.

## Ce qui reste en français

- Articles d'éducation hors chrome, catégories, thèmes et les 22 fiches
  listées dans `docs/i18n-education-status.md` (le catalogue source
  `lib/education/catalog.ts` n'est pas réécrit).
- Titres et corps des notifications déjà enregistrés (générés en français).
- E-mails du cron d'alertes (pas de locale utilisateur).
- `components/BrvmDashboardClient.tsx` n'est plus monté par une route
  (`/marche` utilise `MarketBoardClient`).
